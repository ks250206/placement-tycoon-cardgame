# 実装方針・テスト計画

[設計書一覧](README.md) / [ゲーム設計書](game-design.md)

本書は今後の実装に向けた設計。ゲーム本体・シミュレータ・テストコードを実装済みとするものではない。言語、UIフレームワーク、ホスティング、オンライン対戦方式は未選定。

## 1. 最初に固定する境界

ゲームロジックを画面から分離する。表示上の都合で賞金、カード、影響力、VPを直接書き換えない。

```text
GameState + Action + Ruleset
    → 検証
    → 状態遷移
    → NewGameState + Events
    → 各プレイヤー向けの可視情報へ変換
    → UI / CPU / リプレイ / 集計
```

同じ初期状態、ルール設定、乱数シード、行動列から同じ結果を再現できる構成にする。バランス値は処理本体へ埋め込まず、ルールセットとして分離する。

## 2. 責務の分割案

| 領域 | 責務 |
| --- | --- |
| ラウンド管理 | 準備、2段階配置、配布、試合、精算、終了 |
| 配置 | 手番、残りワーカー、占有枠、費用、合法な購入 |
| 経済 | 現金、賞金、連敗、銀行、投資配当、増員 |
| カード | 物理カードID、確保、シャッフル、配布、手札・場・捨て札 |
| 試合 | 合法手、パス、上がり、方向、特殊効果の処理順 |
| 派閥 | 影響力、契約、共有効果の解禁、同盟、VPアクセス |
| 得点 | 累積配置VPと移動型同盟VPの分離 |
| 可視性 | 公開情報・本人の手札・本人だけの偵察結果 |
| 記録・集計 | 行動履歴、再現、収支、配置率、勝率、所要時間 |

## 3. 状態モデルの最小要素

### ゲーム全体

```text
GameState
  rulesetVersion / rulesetConfig / seed
  roundIndex / totalRounds / phase
  placementOrder / activePlayer
  placementOccupancy
  deckZones
  sharedRulesThisRound
  factionSharedEffectsActive / factionSharedEffectsPending
  allianceOwners
  players
  matchState
  eventLog
```

### プレイヤー

```text
PlayerState
  cash
  permanentVP
  totalWorkers / availableWorkers / workersPlaced
  pendingWorkerUpgrade
  reservedCards / hand
  ownedSkills / equippedSkills
  investments
  influenceByFaction
  mainContract / contractLevelSnapshot
  lossStreak / lastMatchRank
  perRoundUsageCounters
  privateKnowledge
```

表示VPを独立した累積値として手動加算し続けない。累積配置VPと現在の同盟所有から計算することで、トークン移転の二重計上を防ぐ。

## 4. フェーズ管理

```text
ROUND_SETUP
  → RESERVATION_PLACEMENT
  → DEAL
  → INTELLIGENCE_RESOLUTION
  → STRATEGY_PLACEMENT
  → LOADOUT_LOCK
  → CARD_MATCH
  → SETTLEMENT
  → 次ラウンド / ゲーム終了
```

最終得点配置案を採用する場合のみ、最終回のSETTLEMENT後へFINAL_SCORING_PLACEMENTを追加する。未採用のまま暗黙に実装しない。

第1配置のパスは第1配置だけを終了する。第2配置でワーカーが再配布されることはない。フェーズごとのパス状態を別々に記録する。

試合のパス状態、試合内の進行方向、配置順はそれぞれ独立して管理する。

## 5. 行動の検証と会計

配置アクションは、手番、フェーズ、ワーカー残数、枠の空き、資金、前提条件、使用回数をすべて確認してから確定する。

```text
PLACE_WORKER(spaceId, option)
  1. 行動者とフェーズを検証
  2. 枠・資金・能力条件を検証
  3. 料金と適用割引を確定
  4. 支払・ワーカー消費・占有・効果を一括反映
  5. 影響力変化なら同盟と共有効果の解禁予約を更新
  6. 次の配置手番へ進める
```

途中で失敗したら資金やワーカーだけを消費しない。同じ操作の再送で二重購入・二重賞金が起きないよう、ネットワーク対応時は状態バージョンとアクションIDで検証する。

スキル購入と装備、影響力獲得と次回個人バフ、共有効果の解禁予約と実際の有効化は別イベントにする。

## 6. 公開情報と秘密情報

公開状態だけで、相手の現金、確保カード、所有スキル、配置、影響力、VPを確認できるようにする。

未公開の手札や未配布カードの実体を、一般プレイヤー向けの状態へそのまま含めない。CPUにも難易度の名目で相手の手札を渡さず、基本はそのプレイヤーから見える情報だけを入力する。

シードから配布を復元できる場合、対戦中にシードを全員へ公開しない。全情報リプレイの公開は試合終了後など、秘密情報が勝敗に影響しなくなるタイミングに限定する。

諜報による私的な閲覧結果と、全体効果による公開プールを区別する。交換後に古くなった情報を、現在も確実に存在するカードとして表示しない。

封印競りを採用する場合、現金・予約金の公開方法から入札額が漏れない設計が必要。競りを実装する前に、この情報設計まで確定する。

## 7. 最小UI構成

| 画面・領域 | 必要な情報 |
| --- | --- |
| 共通ヘッダー | ラウンド、フェーズ、行動者、配置順 |
| プレイヤー概要 | 現金、VP内訳、残りワーカー、投資、連敗数 |
| カード市場 | 13ランク×4スート、価格、確保済み状態 |
| 戦略盤 | 共有ルール、スキル、銀行、投資、増員、VPの空き枠 |
| 派閥盤 | 各人の影響力、主契約、同盟、共有効果の解禁状況 |
| 自分の手札 | 非公開表示、合法手、発動可能なスキル |
| 試合の場 | 提出カード、革命、11バック、縛り、方向、パス済み |
| 精算 | 基本賞金、連敗ボーナス、次回順、差分 |
| 履歴 | 何に何G払ったか、何VP増減したかを追える記録 |

READMEから起動コマンドを案内するのは、実際に実装・動作確認できた段階からとする。現時点では実行可能なアプリとして扱わない。

## 8. 受け入れテスト

| ID | テスト | 期待結果 |
| --- | --- | --- |
| T-01 | 第1配置で5個中3個使用して配布 | 第2配置で使えるのは2個 |
| T-02 | 4人が異なるスートの2を確保 | 4人とも1枚ずつ確保できる |
| T-03 | 同じ物理カードを再予約 | 拒否。資金もワーカーも変化しない |
| T-04 | 確保3枚で配布 | ランダム10枚を加え、合計13枚 |
| T-05 | 資金不足・占有済みマスへ配置 | 状態が部分更新されない |
| T-06 | 配布後にカード市場へ配置 | 拒否 |
| T-07 | 他人が革命を購入 | 全員に革命の権利を解禁するが、強弱はまだ反転しない |
| T-08 | 試合で1位・連勝 | 賞金だけ増え、試合VPは0 |
| T-09 | 連敗上限到達後に優勝 | 連敗数0、過去の連敗ボーナスは支給しない |
| T-10 | ラウンド末から次回開始 | 賞金を二重支給しない |
| T-11 | 投資購入 | 同ラウンド配当なし、次回から配当あり |
| T-12 | ワーカー増員購入 | 同ラウンドには使えず、次回から増える |
| T-13 | 同盟保持者へ影響力で並ぶ | 保持者は変わらない |
| T-14 | 同盟保持者を追い抜く | トークンと2VPが移り、総量は増えない |
| T-15 | 共有効果の閾値へ到達 | 今回は予約、次回に全員へ適用 |
| T-16 | 個人バフの段階を途中で上げる | 個人バフは次回から、VP資格は現在値で判定 |
| T-17 | 通常の派閥VP利用後に上級交換を要求 | 同じ枠なので当該ラウンドは拒否 |
| T-18 | 個人割引と共有割引を合算 | 支払額の下限1Gを維持 |
| T-19 | 技能ギルドの契約を解除 | 所有スキルは残り、装備上限だけ戻る |
| T-20 | 諜報交換・7渡し・特殊効果を連続実行 | カードの重複・消失なし |
| T-21 | 相手向け表示・CPU入力を生成 | 非公開手札・非公開偵察結果を含まない |
| T-22 | 同じシード・行動履歴を再生 | 同じ最終状態・得点に到達 |
| T-23 | 未定義の方縛り等を設定で有効化 | 明示エラー。黙って別ルールへ置き換えない |
| T-24 | 同盟を何度も奪い返す | 移動型VPが累積しない |

試合の境界条件は [カードルールとタイミング](rules-and-timing.md) の例題も対象にする。上記はテスト要求であり、実行済みという意味ではない。

## 9. 実装の順序

1. **未決定ルールの固定**: 最終得点配置、ジョーカー、縛り系、試合の細則を試作プロファイルとして確定する。
2. **ヘッドレスな基盤**: 状態、配置、会計、配布、派閥、VPを実装し、不変条件をテストする。
3. **大富豪エンジン**: 合法手、パス、上がり、革命、各スキルを段階的に追加する。
4. **ローカル試作UI**: 人間が一巡プレイできる状態を作り、履歴と精算表示を整える。
5. **比較・調整**: シード固定の対戦、席順交換、人間のプレイテストでパラメータを調整する。
6. **拡張判断**: オンライン、観戦、リプレイ公開、追加派閥やスキルは、基本ゲームが成立してから検討する。

ライセンス、技術スタック、公開方式はこの文書では決定しない。まずルールエンジンとテスト可能性を優先する。
